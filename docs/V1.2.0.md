# ClickForge v1.2.0 local candidate

Prepared from public v1.1.2 (`6201f2bfbde18118bfef02076f28fd4985579332`). The checkout was clean before implementation. Existing tags and the public v1.1.2 release notes were inspected; no v1.2.0 tag or release existed. Central version metadata is now 1.2.0. The results below document working-tree verification before the candidate commits; no version tag or GitHub Release has been published.

## Implementation

- The main window now uses the obsidian/champagne design, a responsive navigation rail, and genuine target/profile inspector, labels submitted **input pairs** accurately, and distinguishes configured CPS from actual engine state. Shortcut configuration is an accessible expandable section; active key labels remain on the main actions. Small windows scroll intentionally. Profile and preferences dialogs use the same theme, with dark lists, menus, popups, tooltips and visible focus.
- `TrayService` directly calls Windows Shell notification-area APIs using the existing WPF window/message loop. Its icon is rendered from the embedded ClickForge drawing. It handles Explorer restart, native add/modify failures and idempotent deletion. No new package or UI framework is required. The WPF context menu routes into existing main-window commands, including the existing updater.
- Minimize-to-tray and close-to-tray are separate, conservative opt-in preferences. Hiding stops input; restoring never starts it. Hiding requires an available tray icon and no visible owned dialog. Tray failure preserves ordinary window behavior. Explicit Exit, Windows session ending and updater restart use the coordinated cleanup path. Hidden UI refresh falls from four times a second to once a second; the engine and emergency shortcut remain independent of this refresh.
- `SingleInstance` uses a per-user, session-local Windows mutex and named open event. A secondary ordinary launch signals the current window instead of constructing another engine or icon. Diagnostic launches have explicitly isolated settings and mocked input.
- `TimingProfile` contains only portable timing and activation data. `ProfileStore` keeps one atomic JSON file per UUID, validates each independently, enforces bounds, and reports failures. Applying a validated profile calls the existing engine's synchronous stop barrier, then configures that same worker. Target selection, Roblox-only preference, shortcuts and updater preferences are untouched. The engine stays stopped. Profile create/rename/duplicate/delete/import/export, current-configuration capture, built-in restoration and an active/modified indicator are implemented.
- `UserData` centralizes flushed temporary writes and atomic replacement with shared per-path locks. Existing settings remain in the same file and gain only opt-in tray preferences and an optional active profile ID. Legacy settings receive safe defaults. Invalid settings recover with visible feedback and a redacted activity entry.
- `ActivityHistory` holds 100 predefined timestamped events in memory. No per-click logging, target identity, arbitrary error strings, file paths, tokens or profile names enter its export. Settings exposes a live redacted diagnostic report, activity clearing and explicit export. No background log file is created.
- Standard WPF controls keep keyboard and automation behavior. Fields, sliders, profile controls, icon actions and engine state have meaningful labels; focus indicators are reusable. Dialog Tab navigation is contained, Escape closes without applying draft profile edits, and important engine states expose polite live-region events. No animated transitions are used. The obsidian/champagne palette was checked with sRGB contrast calculations: primary text 16.61:1, secondary text 7.89:1, primary action text 8.46:1 at the darker gradient endpoint, selected timing text 11.08:1 and error text 5.99:1. These calculations do not replace a screen-reader session or an exhaustive accessibility audit.

The production click worker, timing distributions, fixed immediate-first-event path, verified Roblox identity checks, exact variable target/foreground/pointer gates, mouse release and isolated Safe Click Test were preserved. Profile and tray actions have no independent click loop. Activating while the profile/settings editor is open is blocked with an explanation. No startup registration feature was added.

## Portable profile format

JSON property names are case-sensitive. Enumerations use their numeric values: timing 0 Fixed / 1 Variable; activation 0 Toggle / 1 Hold. Export from the manager to obtain a complete valid document:

```json
{
  "SchemaVersion": 1,
  "Id": "8a27a33a-d822-4340-b038-e68922bdf098",
  "Name": "Standard",
  "Description": "A portable timing configuration",
  "Created": "2026-10-25T00:00:00+00:00",
  "Modified": "2026-10-25T00:00:00+00:00",
  "TimingMode": 0,
  "FixedCps": 10,
  "MinimumCps": 5,
  "MaximumCps": 20,
  "ActivationMode": 0
}
```

Every field except Description is required. All rates must be integer 1–50; minimum must not exceed maximum, including when a fixed profile is imported. UUID must be nonempty, timestamps valid with Modified no earlier than Created, names 1–80 characters without control characters, descriptions at most 500 characters. Schema must be exactly 1. Duplicate and unknown properties, malformed input and files over 16 KiB are rejected. At most 100 profile files can be stored. Imports receive a fresh UUID and timestamps, resolving identity collisions without overwriting a current profile. Import selects the copy for review but never applies it.

Files are `%LOCALAPPDATA%/ClickForge/Profiles/<uuid-without-hyphens>.json`; filenames must match the contained ID when loaded internally. An invalid file is skipped without discarding valid peers. A directory filled with invalid files may require manual cleanup before new profiles can be saved. Neither profile data nor settings contain active clicking state or persisted target handles. Profiles contain no application safety flags, shortcuts, executable paths, updater endpoints or commands. Restoring built-ins replaces only the two known built-in IDs and preserves user-created profiles.

## Commands and verification

The following commands were used against this checkout:

```powershell
./build.ps1 -SkipPackage
./scripts/Package-Release.ps1 -OutputDirectory artifacts/v120-final/payload
./scripts/Test-UpdateProcess.ps1 -PayloadDirectory artifacts/v120-final/payload
```

Release builds are checked with warnings treated as errors. The root script runs the complete core and updater test harnesses and actual WPF diagnostics. The diagnostic runner uses a mocked mouse and separate settings/profile directory, writes screenshots, and requires an explicit successful-completion marker. An early process exit cannot count as a completed UI suite.

Verification results and the final local package are recorded in the task completion report. Logs are under `artifacts/logs/`. The two real updater-helper scenarios use disposable fixture processes and files: successful installation/startup acknowledgment, and failed startup with rollback/restart. Both assert byte-for-byte preservation of unrelated settings and profile files. These tests do not replace the user's installation.

The local review ZIP retains the strict seven-entry package contract: app, updater helper, README, three runtime notices and manifest. The new resources are embedded. Local packaging from an uncommitted checkout records the base HEAD in assembly/manifest metadata; it is a review artifact, not proof of an exact committed source tree. An official release still requires reviewing/committing the changes and the existing strict matching-tag workflow.

## Runtime evidence and limits

The actual application was launched at this machine's **150% Windows display scale**. The 1280×920-DIP default layout fit without scrolling; 640×700 and compact profile layouts scroll. Native Shell registration and an icon rectangle were confirmed, and initialization failure, duplicate prevention, menu routing, minimize/hide/restore, opt-in close, emergency routing while hidden and icon removal were exercised through application diagnostics. Those programmatic actions do not prove physical pointer interaction with the notification area.

An additional interactive build used mocked input and disposable settings. Its actual UI Automation tree exposed field names, slider values, disabled Pause, active key labels, profile/settings/update actions and engine status. An OS-delivered F6 changed state from Stopped to Clicking and advanced the mocked counter. The user then stopped Computer Use with Escape; no further Computer Use calls were made. The diagnostic process was closed cleanly. Interactive F7/F8, manual notification-area interaction and keyboard-only completion were not claimed as verified. Internal routed F7/F8 and emergency-while-hidden checks are covered separately by diagnostics.

The current system is 150% DPI. Content-layout scaling was exercised at 125%, 150% and 200%, but those checks are not independent Windows DPI settings. Native 96-DPI, other real display scales, Windows text-size preferences, screen-reader speech, physical keyboard hardware delivery, Explorer-restart interaction, Windows shutdown/logoff interaction and input acceptance in a live Roblox experience remain manual verification items. No test sent automated clicks to Roblox.

Before the obsidian redesign, a separate idle interactive process measured **2.80% of one CPU core**, **116.9 MiB working set**, **78.4 MiB private memory** over **5.035 seconds**, after five seconds of warmup. Short samples taken immediately after the heavy UI diagnostic sequence were substantially higher (roughly 80% of one core in that environment); neither is a general performance guarantee. No performance numbers were inferred from compilation.
